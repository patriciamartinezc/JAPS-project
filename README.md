# JAPS — Practice 1

Authors: Jimena Gil, Ariadna Calzado, Sofía Rodríguez, Patricia Martínez
Resources: garments (main), stores, looks, customers, orders, orderItems (order-items), repairs, reviews, fabrics, workshops

JAPS is a fictional clothing brand from Madrid. This practice adds a REST API (Node.js + Express) to the website we built in Block I, and connects the pages to it with `fetch()`.

## Run it

Requires Node 18+. Nothing else. (The SQLite database uses `node:sqlite`, which is built into Node 22.5 and later; on an older Node the server still starts and keeps the data in memory instead.)

```
npm install
npm start          -> open http://localhost:3000
```

Open the site at `http://localhost:3000`, never by double-clicking an HTML file: the pages call the API with relative URLs (`/api/...`), which only work when the page comes from the same server. The data lives in a SQLite database, the file `japs.db`, which is created the first time the server starts and filled with the seed rows of `src/data/seed.js`. It survives restarts; `npm run reset` deletes the file, so the next `npm start` begins again from the seed data. Node 22 prints an `ExperimentalWarning` about SQLite: that is normal.

## Resources

Every resource has an `id` (generated by the server) and its own router, controller and validator. A fixed list (garment categories, sizes, order statuses...) is not a resource: it is written as a fixed `<select>` and the validator accepts exactly the same values.

### garments   (main resource)

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| name | string | required, non-empty text, at most 60 characters |
| category | string (fixed list) | required, one of: shirts, dresses, skirts, jackets, trousers, shoes, bags |
| price | number | required, number from 1 to 2000 |
| material | string | required, non-empty text, at most 80 characters |
| inStock | boolean | required, true or false only |
| image | string | optional text, at most 120 characters (empty if not sent) |

### stores

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| name | string | required, non-empty text, at most 60 characters |
| city | string (fixed list) | required, one of: Madrid, Barcelona, Porto |
| address | string | required, non-empty text, at most 80 characters |
| hours | string | required, non-empty text, at most 160 characters |
| opensSunday | boolean | required, true or false only |
| image | string | optional text, at most 120 characters (empty if not sent) |

### looks

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| title | string | required, non-empty text, at most 80 characters |
| season | string (fixed list) | required, one of: autumn-2026, spring-2026 |
| description | string | required, non-empty text, at most 300 characters |
| published | boolean | required, true or false only |
| image | string | optional text, at most 120 characters (empty if not sent) |

### customers

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| fullName | string | required, non-empty text, at most 60 characters |
| email | string | required, an email address, at most 80 characters |
| city | string | required, non-empty text, at most 40 characters |
| newsletter | boolean | required, true or false only |

### orders

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| customerId | integer (id) | required, id of an existing customer |
| status | string (fixed list) | required, one of: pending, paid, shipped, delivered |
| country | string (fixed list) | required, one of: Spain, Portugal, Other |
| total | number | required, number from 0 to 10000 |

### orderItems

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| orderId | integer (id) | required, id of an existing order |
| garmentId | integer (id) | required, id of an existing garment |
| quantity | integer | required, whole number from 1 to 20 |
| size | string (fixed list) | required, one of: XS, S, M, L, XL, XXL |

### repairs

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| customerId | integer (id) | required, id of an existing customer |
| storeId | integer (id) | required, id of an existing store |
| description | string | required, non-empty text, at most 200 characters |
| status | string (fixed list) | required, one of: received, in-progress, done |

### reviews

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| garmentId | integer (id) | required, id of an existing garment |
| author | string | required, non-empty text, at most 40 characters |
| rating | integer | required, whole number from 1 to 5 |
| comment | string | required, non-empty text, at most 300 characters |

### fabrics

| Field | Type | Rules |
|---|---|---|
| id | integer | server-generated, ignored if sent |
| name | string | required, non-empty text, at most 60 characters |
| origin | string (fixed list) | required, one of: Spain, Portugal, Italy |
| gsm | integer | required, whole number from 20 to 800 |
| organic | boolean | required, true or false only |

### workshops

| Field | Type | Rules |
|---|---|---|

## Postman

1. In Postman: **Import** → `postman/japs.postman_collection.json`.
2. Start the server (`npm start`).
3. Open the collection and press **Run collection**, in the order it already has. The variable `baseUrl` is `http://localhost:3000/api`, so every URL reads `{{baseUrl}}/garments`.

The first folder is a full CRUD on garments: list, create (it saves the new id in the variable `garmentId`), get one, replace, delete and a final get that must be a 404. The second folder has the invalid POST (400 with the error array), the search and filter, an invalid filter and `/stats`. Run it against a freshly started server (after playing with the site, `npm run reset` and `npm start` give you the seed data back); the requests only touch the garment they create.

## Design decisions

- **Invalid query parameters: rejected with 400 or ignored? Why?** Rejected with 400 and the same `{ errors: [...] }` shape as a bad body. If `?category=hats` were ignored, the client would get every garment and think hats exist (or that its filter worked); a clear error shows the mistake at once. The only exception is an empty value (`?category=`), which counts as "not given" because that is what an empty `<select>` option sends.
- **Where is express.static mounted in app.js, and why there?** After `express.json()` and the logger, and before the `/api` routers. A request for a page or a script is answered right there and never reaches the API; the API paths start with `/api`, so the two cannot collide. The JSON 404 and the error handler come after both, so an unknown page also gets a JSON 404.
- **Why do searching and filtering happen on the server?** The page would otherwise have to download every garment to decide which ones to show. Filtering on the server sends only what was asked for, keeps the rule in one place (the same `?search=` works from Postman and from any other client) and still works unchanged when the list is much longer or comes from a database.
- **Validation lives in two places on purpose.** The browser checks first for instant feedback (it uses `validateEmail` from our Session 8 `exercises.js`), but the server validates every request, because anyone can call the API without the page.
- **A controller checks references.** A validator only says whether the body is well-formed; whether `garmentId: 7` really exists needs the data, so the controller answers 400 `no garment with that id`.
- **The database (bonus): a real SQLite store behind the same `store.js` interface.** Every resource is a table in `japs.db`. `src/data/store.js` gives each table five methods (`all`, `find`, `insert`, `replace`, `remove`) and the controllers only use those, so the routes, the validators and the pages did not change when the arrays were replaced. The ids come from the database (`AUTOINCREMENT`: an id is never reused), booleans are stored as 0/1 and turned back into true/false, and every query uses `?` placeholders so a client can never inject SQL. If SQLite cannot start, `store.js` falls back to in-memory arrays behind the same five methods.
- **Why `node:sqlite` and not a package.** It is built into Node 22, so `npm install` still installs only Express. We first tried `better-sqlite3`, but it has to be compiled during install and that failed on a clean machine.
- **Deleting does not cascade.** Deleting a garment does not delete its reviews or order items; their tables show `#7` instead of a name. It keeps the practice simple, and SQLite foreign keys with `ON DELETE` rules would be the real fix.
